# Mint production acceptance journeys

Source inventory for commit `d607c10a886c37fc94cc9bf64aeddaec77a6a920` (0.6 Preview). The [production roadmap](../../now-to-production-roadmap.md) defines the gates, the [support matrix](support-matrix.json) describes input and operation boundaries, and the candidate baseline records the checks actually executed. This inventory describes how to exercise the shipped surfaces.

**Core** means a candidate for the initial production contract on the primary ELF64/AArch64 and ELF64/x86-64 targets. **Conditional** means the command is shipped and needs a supported format, instruction family, metadata kind, or environment. **Experimental** means shipped preview functionality with narrower evidence. Those labels do not mark any journey as passed. Test names denote supporting coverage. Run the required user journeys in the optimized APK or Play build as well as running automated native tests.

## Android action inventory

The launch and import controls expose Open/Open another, OS `ACTION_VIEW`, Try example, Help (English and Ukrainian), About/licences and Cancel. Import routes are auto-detect, explicit raw mapping, explicit Mach-O CPU slice, and restore project archive. Raw requires a selected decoder, base and entry. The selectable data byte order belongs to the supported AArch64 raw path. Keep auto-detect behavior for the documented DEX/APK bounded preview separate from native qualification. Bad format, wrong slice, unsupported raw mode and cancelled provider input must produce a bounded error or cancellation outcome without damaging the previous Program. `ExampleInstrumentedTest`, `PlatformDeviceTest`, `ProjectArchiveDeviceTest`, `native_loaders`, `loader_depth` and `program_platform` cover parts of this surface.

## Acceptance scripts

Save one result per journey/configuration with source SHA, artifact SHA-256, app version/code, signer digest, device/API/host ABI, target ISA/ABI, fixture digest, result (`passed`, `failed`, `blocked`, `not-run`), and evidence. Record the first failure, including timeouts and skips. Keep private files and full device identifiers out of the report. The fixture locations refer to the repository root.

## Candidate build and verification

1. Record revision and clean checkout status. Use JDK 17, the checked-in Gradle Wrapper 8.13, Android Gradle Plugin 8.11.1, SDK 36, NDK `28.2.13676358` and CMake `3.22.1`. Check `gradle/libs.versions.toml` and `app/build.gradle` for drift. Install toolchains outside the checkout. Define reference devices before testing. The app minimum is API 26; run a minimum-API smoke test and a recent API run, covering both shipping native host ABIs. Record the exact OS and hardware used.
2. Run sanitized host tests, real compiler corpus, JVM/JNI, archive and stateful/fuzz checks. Build Android unit and instrumentation APKs. Use test-only app identities or isolated profiles when certificates differ from installed apps. Never uninstall a user's Mint or clear its data to qualify an upgrade. Test process death and storage failures only against fixtures. The [test runner](../../app/hosttest/run.sh) and [corpus instructions](../../quality/corpus/README.md) describe build commands and fixture positions.
3. Build `./gradlew :app:testDebugUnitTest :app:assembleRelease :app:bundleRelease` with existing private signing configuration. `:app:assembleUnsignedRelease` is useful for local optimized build qualification. Keep unsigned output, debug APKs, and private-phone builds away from the publication paths. Release variants have R8 minification and resource shrinking. Capture output artifacts and R8 mapping privately. Verify the manifest says `com.ccs.mint`, the intended `versionName` and a monotonically increasing `versionCode`, and that this is not a debuggable APK.
4. Run `apksigner verify --verbose --print-certs` and `zipalign -c -P 16 -v 4` on the APK. Run `jarsigner -verify` on the AAB (or use its trusted signing key validation) and validate the bundle manifest and ABI content. Record SHA-256 of the files and cert identities. Check both artifacts contain the correct native host payloads. Test native load and app behavior separately from structural alignment and package verification.
5. Capture J01–J09 results and full failures/blocked/skipped cases. For release, associate the exact GitHub tag, APK digest and notes or Play track/build and installed app-signing cert with the revision. Preserve confirmed previous artifacts for comparison. Check upgrade compatibility before installing anything on a user's phone. Documentation, privacy/support/security and signing-key recovery requirements remain tracked by the production roadmap.

## Coverage to close before 1.0

The source inventory and component tests establish the baseline scope. The production gate still requires the optimized device journeys, broader repeatable device and compiler coverage, migration and rollback policy, suite reproducibility from a clean environment, and 14-day RC soak. Register observed defect and acceptance coverage gaps in the release issue register. Keep accepted alternate/preview capabilities separate from primary production results.
